# RAG Live Validation Guide

Updated: 2026-05-19

This guide is the operator-facing live validation path for RAG knowledge ingestion. It is meant for workstation users and server maintainers who need to prove that upload, text ingest, retrieval, debug, reingest, and source cleanup work together on a real running stack.

## Scope

Phase 60G validates the existing RAG runtime without changing backend semantics. It uses the live API server, PostgreSQL, Qdrant, and the active embedding provider.

Validated API surfaces:

- `POST /api/v1/files/upload`
- `POST /api/v1/rag/ingest`
- `GET /api/v1/documents`
- `GET /api/v1/documents/{document_id}`
- `POST /api/v1/rag/search`
- `POST /api/v1/rag/debug`
- `POST /api/v1/documents/reingest`
- `DELETE /api/v1/documents/by-source/{source_id}`
- `GET /api/v1/rag/collections`
- `GET /api/v1/rag/embedding/health`

## Test Collection

Use an isolated collection so validation data does not mix with real knowledge:

```text
phase60g_live_validation
```

Recommended headers:

```text
X-Workspace-Id: demo-workspace
X-User-Id: demo-user
```

## Test Knowledge Files

Prepare temporary files outside the repository. Do not commit generated validation files.

Recommended coverage:

- TXT with the anchors `phase60g`, `golden upload path`, `approval wait`, `rerank debug`, `source cleanup`.
- MD with a small operator runbook.
- CSV with checklist rows for upload, search, debug, and cleanup.
- DOCX generated by a normal office editor or `python-docx`.
- PDF generated from an office document or HTML through LibreOffice.

The Phase 60G live run used a temp directory under `%TEMP%` and uploaded TXT, MD, CSV, DOCX, and PDF successfully.

## Workstation User Flow

1. Open Admin Dashboard `RAG / Documents`.
2. Confirm embedding health is reachable.
3. Set the collection to `phase60g_live_validation`.
4. Upload a file or use text ingest.
5. Refresh the document list and confirm `status=active`, `ingest_status=completed`, and `chunk_count` is greater than zero.
6. Run hybrid search with:

```text
phase60g golden upload path approval wait rerank debug source cleanup
```

7. Open retrieval debug for the same collection and confirm returned chunks and scores.
8. Use reingest only when replacing the same `source_id`.
9. Use delete-by-source only after typing the exact `source_id`.

## Server Maintainer Flow

1. Confirm Docker services are running: API, PostgreSQL, Redis, Qdrant, and browser worker.
2. Check API health:

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/health"
```

3. Check embedding health:

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/rag/embedding/health"
```

4. Upload each supported file type with `/files/upload`.
5. List documents for the validation collection.
6. Run `/rag/search` and `/rag/debug`.
7. Reingest a known manual source through `/documents/reingest`.
8. Create a dedicated delete-check source, then remove it with `/documents/by-source/{source_id}`.
9. Confirm only the delete-check source was removed.

## API Examples

File upload:

```powershell
$base = "http://127.0.0.1:8000/api/v1"
$collection = "phase60g_live_validation"
$path = "$env:TEMP\phase60g-operator-note.txt"

curl.exe -sS -X POST "$base/files/upload" `
  -H "X-Workspace-Id: demo-workspace" `
  -H "X-User-Id: demo-user" `
  -F "file=@$path" `
  -F "collection_name=$collection" `
  -F "duplicate_strategy=force_reingest" `
  -F "chunk_size=420" `
  -F "chunk_overlap=40"
```

Text ingest:

```powershell
$headers = @{ "X-Workspace-Id" = "demo-workspace"; "X-User-Id" = "demo-user" }
Invoke-RestMethod -Method Post -Uri "$base/rag/ingest" -Headers $headers -ContentType "application/json" -Body (@{
  text = "phase60g manual text ingest validates operator guidance and source cleanup."
  metadata = @{ phase = "60G"; validation = "manual-text" }
  source_id = "phase60g-manual-text"
  source_name = "Phase 60G manual text note"
  source_type = "manual"
  collection_name = $collection
  chunk_size = 420
  chunk_overlap = 40
} | ConvertTo-Json -Depth 10)
```

Hybrid search:

```powershell
Invoke-RestMethod -Method Post -Uri "$base/rag/search" -Headers $headers -ContentType "application/json" -Body (@{
  query = "phase60g golden upload path approval wait rerank debug source cleanup"
  collection_name = $collection
  search_mode = "hybrid"
  dense_top_k = 20
  keyword_top_k = 20
  final_top_k = 5
} | ConvertTo-Json -Depth 10)
```

Retrieval debug:

```powershell
Invoke-RestMethod -Method Post -Uri "$base/rag/debug" -Headers $headers -ContentType "application/json" -Body (@{
  query = "phase60g source cleanup and replay diagnostics"
  collection_name = $collection
  top_k = 5
} | ConvertTo-Json -Depth 10)
```

Reingest:

```powershell
Invoke-RestMethod -Method Post -Uri "$base/documents/reingest" -Headers $headers -ContentType "application/json" -Body (@{
  text = "phase60g reingest validates same source replacement and updated operator note."
  metadata = @{ phase = "60G"; validation = "reingest" }
  source_id = "phase60g-manual-text"
  source_name = "Phase 60G reingested manual text note"
  source_type = "manual"
  collection_name = $collection
  chunk_size = 420
  chunk_overlap = 40
} | ConvertTo-Json -Depth 10)
```

Delete one known test source:

```powershell
Invoke-RestMethod -Method Delete -Uri "$base/documents/by-source/phase60g-delete-check?collection_name=$collection" -Headers $headers
```

## Pass Criteria

- Every uploaded file returns `ingest_status=completed`.
- Every successful file or text source has at least one chunk.
- Search returns the validation anchors from the expected collection.
- Debug returns embedding dimension and score details.
- Reingest creates a newer version for the same `source_id`.
- Delete-by-source removes only the explicitly confirmed test source.
- Generated test files and result JSON stay outside the repository.

## Boundaries

- This guide does not add OCR, PPTX, XLSX, image ingestion, or new parsers.
- This guide does not add auth, RBAC, or permission UI.
- This guide does not change retrieval ranking, chunking, or embedding semantics.
- Mock embedding and mock reranker are valid for infrastructure validation, but they do not prove production retrieval quality.
